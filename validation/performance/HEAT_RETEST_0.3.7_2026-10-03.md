# 0.3.7 两局发热与通知标记复核

日期：2026-10-03。两份诊断日志来自同一台 vivo V2282A / Android 13（API 33），应用均为 0.3.7（versionCode 15）。配置 profile 为 `0.9.1-yolox-nano-dual-512-v6-near-zone`。测试者反馈两局都明显发热、手机烫手，第二局尤甚。

用户确认两局及此前测试均一直开启手机热点，因此热点是已知的固定测试条件，不能据此解释版本之间的发热变化。两局仍缺充分冷却及旧版相近起始温度的独立对照，尚不能量化版本温升差；本轮继续针对听野处理负载与温控策略修正，无需把关闭热点作为默认复测要求。

## 发热与处理负载

第二局 `audit` 中的 `CaptureLoadControl mode=WARM batteryTempTenthsC=433 thermalStatus=0 restMs=190` 明确记录于会话开始后 270.980 秒。这是应用处理温度样本后的模式转换记录，不能当作电池达到该温度的精确时刻。随后 275.691 秒的检查点记录 WARM；270.680 秒检查点仍为 NORMAL，当时设备采样已为 43.3°C。旧策略以电池温度 43°C 进入 WARM、45°C 进入 HOT；本局最高 43.9°C，未到旧 HOT 门槛。结合用户的烫手反馈，旧门槛显得偏晚，支持提早降载的方向。

记录到的处理墙钟占会话 74.1% 和 69.3%，每帧 Native 处理均值约 296/317 ms，说明本次追踪到的主要持续负载落在 Native 帧处理链路。日志未将纯模型推理从预处理、其他 Native 工作中拆分，因此不能断言纯推理是唯一或已确定的主因。上下文图像复制累计 1.894/2.792 秒；截图采集、编码或写盘也可能增加负载，但日志没有完整诊断 I/O 计时，也没有关闭截图的同机对照，贡献尚未确认。

每局各有一次上下文请求限流，故相应窗口前后证据不完整；其余图像均在 ZIP 中可用，且 `dropped_events` 与 `dropped_image_requests` 均为 0。派发 12/12、19/19 被应用记录为 ACCEPTED，但派发或应用回调不证明用户实际看见、听见或感到提示。

## “通知没看到”与标记入口

提供的通知截图处于折叠态，没有展开后的操作按钮区域。0.3.7 基线源码通知 action 顺序中，“标记问题”是第二个 `.addAction`，在“暂停/继续”之后；折叠截图与零条 `user_marker` 记录都不能证明按钮缺失。要显示操作项，请先下拉打开 Android 通知栏，找到持续运行通知，再向下拖动该通知卡片或点卡片上的展开箭头；部分系统也支持双指在卡片上向下展开。展开后选择“标记问题”。

两局的 `user_marker` 都为 0，因此没有手动确认的漏报时间点，无法把“没看到”归到某条检测、派发或呈现路径；此处不推断按钮不存在、系统故障或提示实际播放成功。截图不包含持续录像，图像限流也使对应上下文不完整。
