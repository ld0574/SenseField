# 真机视频对拍记录（开心消消乐实战录屏）

本文件是代码里 6 处 `REAL_VIDEO_FINDINGS.md` 引用的落点（`Match3Sampler.autoDetectBoard`／`detectGridCount`、`Match3LiveService` 两处、`CloudVision`、`Match3AutoDetectTest`）。只记文字与数字：**真机截图和录屏一律不入本仓**（隐私与体积），帧提取在仓外临时目录完成。

## 复现方式

```bash
cd research/board-recognition/java-bench
bash run.sh                      # 同步仓库源文件（sha256 核对）＋编译
java -Dsun.stdout.encoding=UTF-8 -cp out com.openkhub.sensefield.RealFrame <真机帧.png>
# 带真值逐格诊断：RealFrame <png> 7 7 14 38 87 71 <49 字符真值>
```

`RealFrame` 不带真值时也会打印：默认手工标定 8×8 的读数、`detectGridCount(默认框)`、`autoDetectBoard` 的框、`detectGridCount(auto 框)` 与自动框＋自检格数下的读盘和成品播报。

## 素材

领导提供的三段真机录屏（开心消消乐第 3 关，7×7 棋盘，仅 4 种动物：棕熊／小鸡／青蛙／蓝河马），1fps 抽帧后取若干静止帧对拍。画面 576×1280（抽帧缩放后）。

## 症状 → 两个生产级缺陷（均已修，`e485fed`）

1. **自动格数自检每帧必崩**：`detectGridCount` 里 `frame.getPixels(rowBuf, 0, cw, x0, y, cw, 1)` 把 `stride`／`offset` 写反（签名是 `getPixels(colors, stride, offset, x, y, w, h)`），真机稳定抛 `ArrayIndexOutOfBoundsException: Index 529 out of bounds for length 529`；异常被实时 tick 的 `catch (Exception e) { Log.w(...) }` 吞掉，只剩一行 warning。后果：自动格数从来没生效过，永远回退固定 8×8。
2. **最小播报间隔内的走子被永久吞掉**：`MIN_ANNOUNCE_GAP_MS`（6s）闸门判断之前就先写了 `lastAnnouncedMatrix = matrix`，被闸门拦下的那帧从此被标记成「已播过」。视频实锤：t=21s 有 18 格变化（一次真实走子），之后无播报；t=30.8s 播出的是过时的犹豫提示。

### 音频节拍证据（解释「同一句话一直重复报」）

- 播报起点间隔实测 **15.0–15.3 s**，正好等于 `IDLE_HINT_MS = 15000` → 反复听到的是犹豫提示按 15s 定时重播，不是局面更新。
- 音频包络相似度：局面播报 vs 犹豫#1 = **0.286**（内容不同）；犹豫#1 vs 犹豫#2 = **0.715**（同一模板），与 `hintCount < 2` 上限一致。
- 棋盘像素在 t=1..16 完全不变 → 那段时间只有定时器在说话。

## 修后实测（同一批真机帧）

| 逐格读数 vs 人工目视标注 | **49/49**，7 行全部「错0」 |

格心平均色按字母聚成四簇，且**远离 HSV 分桶边界**：

- 棕熊 `O`：h 28–29°，s 0.84–0.86，v 0.77–0.82，心-角色差 d 81–101
- 小鸡 `Y`：h 52–56°，s 0.65–0.72，v 0.89–0.97，d 97–120
- 青蛙 `G`：h 105–107°，s 0.73–0.78，v 0.79–0.82，d 74–79
- 河马 `B`：h 191–192°，s 0.75–0.76，v 0.88–0.89，d 72–108

**这条聚簇本身就是几何正确的证据**：若 7×7 被按 8×8 切（或框选偏了），格心会落在格缝与棋子边缘上，同一字母的色相必然被抹开、并出现大量弃权格。旧路径（默认 8×8）读出来正是那样——整行整行报「蓝、蓝、蓝、蓝、蓝、蓝、蓝、蓝」（棋盘底色越过 HSV 闸门被认成河马）。

## 边界条件（用之前要知道）

- `detectGridCount` **只在按棋盘裁剪后的框内可信**。喂默认宽框（`4/18/96/82`，含天空与底部道具栏）会返回 **9**——不是崩溃、是自信地数错。调用方必须先有正确的 `autoDetectBoard` 框，格数自检才是增益而不是灾难。
- 动画未落定的帧（例如本批 `f002`）在 7×7 下读出大量 `'.'` 与底色 `'B'` 混杂 → 三帧逐格多数票（`STABLE_FRAMES = 3`）是承重结构，撤不得。
- 人工真值是先看过机器矩阵再逐格目视标注的，所以 49/49 只支撑「几何对齐正确」，不单独充当「颜色分类正确」的盲测证据；后者由上面四簇远离桶边界来支撑。

## 空位阈值真机标定（10-05 深夜，10fps 密抽帧）

上面那批是 1fps 抽帧。这轮改成 **10fps 密抽**（三段共 1235 帧），逐格跑 `centerCornerDistance` 与生产同款试采闸门，专门回答 `BLOCKED.md` §7 悬着的「阈值 12 到底对不对」。

工具（都在 `java-bench/`，几何一律复用仓库代码，不另算一套）：

```bash
# 逐格中心-四角色差分布 → cells.csv（60134 行）
java -cp out-crops com.openkhub.sensefield.EmptyCalib dense/03457769 dense/445cbe33 dense/cbf4bfa6 > cells.csv
# 生产同款「采纳前试采」闸门复现 → guard.csv（1235 帧）
java -cp out-crops com.openkhub.sensefield.GuardProbe <空filesDir> dense/03457769 dense/445cbe33 dense/cbf4bfa6 > guard.csv
# 按 d 区间挑格、裁图、拼带序号联络表供人工目视
java -cp out-crops com.openkhub.sensefield.EmptyCrops dense cells_xxx.csv outDir dMin dMax n
```

### 结论一：阈值 12 是对的，只能往下调不能往上调

55860 个**格数正确**（7×7）帧格上的 `d` 分布：

| `d` 区间 | 格数 | 目视标注（联络表 96 格抽样） |
| --- | --- | --- |
| ≤ 12 | **4** | 2/3 抽样目视确认是空棋盘底（带邻格棋子压边），第 3 个是跨格边界被切歪的青蛙 |
| 13–59 | 322 | **全部不是空格**：棋子整体相对格心偏移（顶行与最右两列尤其多，是 `(r-l)/n` 取整累积漂移）、雪块/冰块类障碍贴图、以及遮罩弹窗 |
| ≥ 60 | 55534（99.42%） | 有棋子 |

把阈值往上调是纯粹的伤害：调到 20 / 40 / 59 会分别多把 **16 / 57 / 322** 个真棋子念成「空」。所以 `EMPTY_COLOR_DISTANCE = 12` 保持原值，判据已写进该常量的注释里防止后人凭感觉调。

### 结论二：40% 试采闸门实测余量很大，但自我修复那条的分母算错了

`guard.csv` 按帧分类（1235 帧）：

| 帧类别 | 帧数 | 未知格占比 | 40% 闸门 |
| --- | --- | --- | --- |
| 格数正确（`gridN=7`，框 `14/38/87/71`） | 1140（92.3%） | 0–10%，均值 **0.09%** | 全部采纳 ✓ |
| 格数错（`gridN=8/6/9`，框全是 `0/9/100/54`） | 68（5.5%） | **55–75%**，均值 71.6% | 全部拦下 ✓ |
| 检不出棋盘 | 27（2.2%） | — | 走 ABSTAIN |

错格那 68 帧的成因是**小爱同学语音助手遮屏**：联络表里成片白色面板带「小爱」字样，半屏被盖住 → 深蓝遮罩失效 → `autoDetectBoard` 交出 `0/9/100/54` 这种含天空和道具栏的宽框 → `detectGridCount` 自信数成 8 或 9。这正是上面「边界条件」第一条预告过的失效模式，而 40% 闸门把它兜住了（最坏 55% vs 最好 10%，15 个点余量），所以**不改阈值**。玩家用语音助手是常态动作，不是边角情况，这条值得记着。

顺带修掉一处真算错的：自我修复分支里 `countUnknown(fixed) * 100 > total * 40` 用的是**旧**矩阵的格数做分母。新旧格数不同时阈值就跟着错——旧 8×8=64、新候选 6×6=36 时门槛实际变成 71%，一个几乎全未知的 6×6 标定能被采纳。已改成用 `fixed.length * fixed[0].length`（`Match3LiveService.java:370`）。

### 这条标定不能证明什么

- 视频是 576×1280 压缩态，缩放会把格心像素和邻格混色，`d` 的绝对值在真机原分辨率上会整体偏移。所以本轮证明的是「**12 相对真机美术的分布位置正确、且方向上不能放宽**」，不是「12 这个数值在真机原分辨率上最优」。
- 真空位只在动画瞬间出现，而三帧多数票本来就会把那种帧滤掉——所以「空」这个词在真实对局里几乎念不到（1140 帧里总共 4 格），这是正确行为而不是漏报，但也意味着**再多的视频帧也标定不动这个阈值**，§7 想靠攒截图进一步精调的路走不通。

## 已顺手修掉（同晚，播报词表统一）

- **词表分裂已消除**：`Match3Board` 自带的那套颜色词（红橙黄绿蓝紫）删掉了，逐行扫描改走 `Match3Coach.pieceName`——全项目只剩一个命名来源（动物名＋玩家学过的特殊棋子名）。本文件上面那张真机帧读盘，现在念作「第 1 行：棕熊、小鸡、青蛙、河马、小鸡、青蛙、棕熊」，与游戏顶部目标栏的动物图标同一套叫法。
- **「没棋子」与「认不出」分家**：采样器原来把两者都写成 `'.'`，于是逐行播报把玩家学过的特殊棋子念成「空」。现在 `Match3Sampler.EMPTY_CELL = ' '`（格心与四角同色 → 确认空位）与 `UNKNOWN = '.'`（认不出）分开，念成「空」和「未识别」两个词；自我修复检测改按 `isUnreadable()`（两者都算），口径与分家前一致，不会因此漏触发。

## 特殊棋子进不了走法推荐（同晚，分家暴露出来的另一半）

词表分家之后才看得见的问题：`Match3Board.isPiece` 写死只认 `ROYGBP` 六个基础色字母，而采样器给玩家学过的特殊棋子分配的是 `1-9`/`a-z`。于是那些字母在 `findRuns` 与 `findSwaps` 里**等于不存在**——提示永远只推荐普通动物的交换，涉及特效棋子的走法一次都没被推荐过；同时 `'.'` 和 `' '` 反而被当成「非棋子」以外的东西混在枚举里。

改成 `isPiece(c) = !Match3Sampler.isUnreadable(c)`：同字母即同棋子，特殊棋子按自己的字母参与三连；空格与未识别两态明确不参与。`PIECE_COLORS` 常量随之删除（全项目无其它引用）。`Match3BoardTest` 补三个用例锁住：三个相同特殊字母要成三连、涉及特殊棋子的交换要出现在候选里、`'.'`/`' '` 永不计入棋子。

对上面那批真机帧的实际影响：格数正确的 1140 帧里只有 4 格 `' '`、48 格 `'.'`，其余 55808 格全部参与走法枚举——修前这 55808 格里凡是特殊棋子字母都被无声丢掉。
