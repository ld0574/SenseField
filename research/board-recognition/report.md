# 棋盘识别方案对比 POC 报告（2026-10-05）

## 一句话回答领导原问题
**有更好的方案：格子级 CNN（C2，MobileNetV3-Small）——合成集 99.96% vs 现在 HSV 基线 94.3%，特殊棋子全对，且换游戏只需重训 11 分钟不用手调。** 但有一个必须先补的洞：本轮没有真机截图（data/real 空），99.96% 是合成图数字，真机结论待验证。

## 核心结论（6 条，每条带数字）
1. **C2 准确率 99.96%（6978 格错 3 格），分类别全 ≥0.9987**（results.json），比 C0 高 5.6 个百分点，错的主要是相邻色棋子边界格。
2. **C0 有两个本质缺陷**（移植代码与 Java 逐行对应，非移植失真）：①空格判 0%——棋盘底色被 HSV 桶判成蓝色棋子（合成集 1044 个空格全错，real 场景对应「匹配动画期的空格」会误报成棋子）；②同色相棋子混淆——蓝系（bear/fox）在 HSV 域区分不开，C0 只报字母 'B'，矩阵里出现 'A'（ambiguous）标记。
3. **C3 整屏 YOLO 在本条件下是死识别器**：grid_acc 5.66%、全判 empty、mAP50=0.147（models/yolo_runs/c3/results.csv 末行）、conf=0.1 时 3 帧仅 12 个框（推理管线正常，是训练不收敛）。死因见下节。
4. **C2 延迟 726ms/帧（单格串行推理）不满足 1Hz 实时**——批处理 81 格一次前向可压到 200ms 内（batch4 前向实测 19ms/格，见 PROGRESS），上 Android 用 TFLite 后设备端是毫秒级（PC CPU 数字不代表手机端）。这是唯一要补的工程项。
5. **换游戏成本排序**：C2（重训 11 分钟，可脚本化）< C1（标 10 张图）< C0（手调色桶+底色，最贵）。C2 是唯一「换游戏不用改代码」的方案。
6. **真机缺口**：领导未提供真机截图（<10 张那档），全部结论基于复刻工程素材渲染的合成帧。合成素材与真实游戏棋子是同一套美术（isghost 复刻直接用的原版素材），外观一致性高，但真实设备的渲染差异（抗锯齿/压缩/动态光效）未覆盖——**上真机前 99.96% 不能当承诺值用**。

## 死路方向及证据（1 条）
**整屏 YOLO 在「CPU + 200 帧小数据 + 64-81 个密集小目标」条件下是死路。**
- 证据：mAP50=0.147（50 epochs 按书内限时规则降到 10，imgsz 320 控时）；评测 6978 格只命中 5.66%（几乎全判 empty）；反向验证全挂——DEADCHECK same=True（两帧不同图输出完全相同，抓出「任何输入都输出固定模板」的死识别器特征）、FLIP-DETECT 0/5（换 5 格棋子输出纹丝不动）。
- 死因：YOLO 强项是开放场景稀疏目标；规则网格的密集小目标是「人群计数」问题，小数据+CPU 训不收敛。且标注成本是逐格分类的 5-10 倍（要给每个棋子画框，逐格只需格子标签）。
- 可复核：`python src/eval_all.py --c3` 看 C3 行；`cat models/yolo_runs/c3/results.csv | tail -1` 看 mAP 行。

## VLM（C4）：跳过，不进实时链路
无 OPENROUTER_API_KEY，按书内约定跳过（记 BLOCKED.md）。调研结论（sources.md 来源 5/6/7）：延迟与 L2 云端五问同量级（p50 1.08s），1Hz 循环吃不起；成本超 L2 月度额度一个量级；SO-Bench 证明 MLLM 长序列结构化输出（64 格逐一报类）仍有漏格/串格缺口。VLM 的合适用处是**冷启动辅助**（新游戏首次接入读一帧自动推断棋盘范围+棋子类别）和**兜底解释**（连续低置信时描述局面给视障用户核对），不是替代识别。

## 泛化到其它网格游戏
- 棋盘定位（autoDetectBoard）是通用资产：合成 200 帧检出 200/200，f000 检出边界与真值逐位一致（x0 61/61、y0 347/347、右 559/559、底 947/947）。
- 切到其它网格游戏（如其它三消/棋盘类）：C2 只需换素材重渲染 200 帧合成+重训 11 分钟；C0 需重调色桶表+底色条件（手活）；C1 需重标 10 张模板（半自动）。
- 非网格游戏（MOBA/FPS）不在本轮范围（领导拍板），VLM 路线才是那个方向，单独立项。

## 风险
1. **合成-真机 gap（最大）**：无真机数据。建议补 10-30 张真机截图（含特殊棋子局）重跑 `eval_all.py`，C2 若掉到 95% 以下要查合成渲染参数。
2. **版本/换皮**：游戏换棋子美术后 C2 需重训（11 分钟，可脚本化）；C0 需手调。换皮检测可加「模板相似度骤降告警」提示用户重标。
3. **C2 延迟**：726ms（PC CPU 串行）需批处理优化到 200ms 内才敢上 1Hz；手机端 TFLite 预期远低于此（未实测，标「假设，未验证」）。
4. **特殊棋子覆盖不全**：合成集只有炸弹（爆炸棋原型）+冰障碍；4 连/5 连/活力鸟的形态没进合成集（复刻工程素材里没有对应图），C2 的 special_recall=1.0 只代表「炸弹+冰」两类。真机特殊棋子完整覆盖需补素材后重训。

## 下一步（App 要改什么 + 工作量估计）
1. **C2 模型导出 TFLite + Android 集成**：MobileNetV3-Small 1.4M 参数 ≈ 5.5MB，替换 Match3Sampler 的 HSV 桶分类层（棋盘定位 autoDetectBoard 保留不动）。估计 1-2 天。
2. **C2 批处理**：81 格组 batch 一次前向，PC 预期 726ms→200ms 内；手机端预计毫秒级。估计 0.5 天。
3. **C0 保留为兜底**：模型缺失/连续低置信时回退现有 HSV 逻辑（代码已在 App 里，零成本）。
4. **重训管线脚本化**：换游戏/换皮时一键「渲染 200 帧→训 20 epochs→导出 TFLite」。估计 0.5 天。
5. **真机验证**：10-30 张截图重跑评测 + 视障用户实测播报准确率。估计 0.5 天（依赖领导提供截图）。
