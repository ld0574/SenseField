# 版本命名规范

从下一次构建交付起，应用版本统一使用 `a.b.c` 三段数字，例如 `0.3.0`、`0.3.1`、`0.3.2`。

## 每个新版本都递增

- 内部诊断、队友测试、患者试用和对外发布共用一条版本序列，不分内部、外部编号。
- 每交付一个包含新改动的版本，都递增版本号。通常递增最后一位：`0.3.0 → 0.3.1 → 0.3.2`。
- 同一份代码的重复构建和核验不算新版本；交付后再修改代码、配置或模型资产，则必须使用下一个版本号。
- 较大功能迭代可递增第二位并将最后一位置零，例如 `0.3.2 → 0.4.0`；第一位用于整体大版本变化。
- 不在版本号中添加 `alpha`、`beta`、`diagnostics`、`guide`、`internal`、日期或其他后缀。

## 用途与稳定性另外说明

| 版本 | 用途示例 |
| --- | --- |
| `0.3.0` | 既有功能基线 |
| `0.3.1` | 已交付的内部诊断和提醒语音说明测试 |
| `0.3.2` | 本轮内部候选：独立周期检查点、异常记录恢复和密集战斗评分修正 |
| `0.3.3` | 操控期间漏报修复；队友反馈预警改善，日志显示严重升温 |
| `0.3.4` | 处理间歇与低频截图；队友反馈发热改善，瞬时问题的截图上下文不足 |
| `0.3.5` | 当前内部候选：有界事件前后采样和通知人工标记，待同机复测发热与诊断覆盖 |
| `0.3.6` | 下一次包含新改动的交付 |

“内部诊断”“患者试用”“正式发布”写在交付记录、Release 描述或文件类型标签中。使用三段数字并不代表通过稳定性验收，患者试用和正式发布仍遵守真机门禁。

## 构建与交付时同步检查

1. `android/app/build.gradle` 中的 `versionName` 是应用版本；必须符合 `a.b.c` 格式。
2. Android `versionCode` 是安装升级序号，每个新版本递增，不因版本号变化而重置。本轮 `0.3.5` 使用 `versionCode=13`；下一版至少为 `14`。
3. 同步 `scripts/build_android_preview.sh` 中的版本号和升级序号，避免交付旧包。
4. APK 文件名、SHA-256 校验文件、验证记录和发布说明必须对应同一次构建。允许文件名使用 `debug-candidate` 等标签来说明签名类型，应用版本本身仍为 `a.b.c`。
5. Git tag 仅在明确需要时创建；提交代码和递增应用版本不要求创建 tag。

旧记录中的 `0.3.0-alpha.1`、`0.3.0-alpha.1-diagnostics` 和对应 APK 文件名保留原样，作为当时的构建证据，不回改历史版本号、哈希或签名记录。
