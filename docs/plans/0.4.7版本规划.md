## P0：提示稳定性

### W1 — 建立可复查的提示链路

复用 `DiagnosticRecorder`、`CueDispatcher` 和现有离线复盘，按游戏、会话、提示／事件版本及 cue ID 关联：输入新鲜度、门控状态、候选产生、渠道准入、排队、开始、完成、取消、故障和恢复。

- 消消乐继续区分几何确认、HUD 确认、动画、未知格、无准入走法、提示就绪和语音状态。至少 10 秒的等待段沿用现有长门禁口径，完整会话与截断会话分别报告。
- 王者记录当次保存的措辞／渠道开关、密集状态、事件新鲜度、去重和排队替换依据。诊断解释实际使用的偏好，而非仅记录最终短句。
- 同一 cue 的软件请求、系统回调和外部听感各自统计。`STARTED`／`COMPLETED` 表示软件回调，实际听见仍需独立证据。
- 对旧日志缺失的字段输出缺失；未识别的原因保持未知。复盘输出脱敏汇总，原画面与日志留在私有目录。

**验收**：已有日志重建出可追溯的长等待段与播放终态；新增反例覆盖回调乱序、缺回调、停止／换局／换游戏、旧 cue、关闭渠道、故障恢复和截断记录。分类计数与原事件逐项相符，报告能指出缺少哪段证据。

主要入口：[Match3LiveService](../../android/app/src/main/java/com/openkhub/sensefield/Match3LiveService.java)、[CueDispatcher](../../android/app/src/main/java/com/openkhub/sensefield/CueDispatcher.java)、[CaptureService](../../android/app/src/main/java/com/openkhub/sensefield/CaptureService.java)、[离线复盘](../../python/match3/diagnostics_audit.py)。

### W2 — 修正实际复现的提示中断与恢复问题

先以 W1 的结论选取失败片段，再用生产状态机和可控时钟／播放器复现。重点核查已排队提示在尚未播放时取消、TTS 恢复后有效提示能否再次请求、HUD 短暂未读、局部动画与交换证据失效、王者密集模式切换，以及辅助停止后的迟到回调。

恢复提示必须继续满足当前棋盘／事件、目标、几何、会话、时效和已保存开关。现有消消乐 6 秒播报间隔、3 次尝试上限作为初始冻结策略；仅在明确复现说明需要调整时单列改动及对照结果。关闭语音属于用户选择，避免将其记为播放失败或触发重试。

**验收**：每项修改先保留失败复现，再验证修复。冻结片段中的稳定合法提示在首个满足准入和节流的周期提出请求；仍有效且具备播放条件的请求有明确终态。过期、换局、停止、设置禁用和实际交换发生后，旧提示不会开始或补播。王者两字开关关闭时，密集与普通场景均使用完整措辞；开启时按已保存偏好执行。高亮与语音引用相同提示版本和坐标。

继承[三局反馈修复](../development/消消乐三局反馈修复_2026-10-13.md)与[王者开关更正](../../validation/protocols/COMPLIANCE_IMPROVEMENT_2026-10-13.md)，新增回归验证生命周期组合，避免重复建设已修功能。

## P0：视觉感知改进

### V1 — 改善影响实际提示的视觉误识与过度弃权

先把已有发光青蛙、灰毛球密集、末块雪块、魔力鸟／直线特效以及王者实局记录整理为冻结的视觉反例清单。每项记录原画面 SHA、对局来源、可见状态、基线输出和预期；标签含歧义时保留待核对。历史开发素材继续用于开发回归，独立验收语料另行登记。

**消消乐优先实施方向**：

1. 在已有脸／完整外观和家族库之上，核查发光动物的颜色、特效类型／方向与覆盖层是否分别有依据。对已确认的难外观，沿用现有审阅→编译流程补家族代表样本；根据实际失败原因选择局部结构复核，保持原图库预算和准入阈值。显示底层动物与授予交换／匹配权限分别验收。
2. 检查闪光、毛球覆盖变化与真实交换／下落在运动判定中的混淆。外观闪烁只有在当前结构证据支持时才能保持身份；移动、空位、换色和未知覆盖仍使相关证据失效。验证局部未决格能否保留与它无关的可靠走法，同时保留对连消与跨区域特效依赖的检查。
3. 对影响首选动作和最后目标的未决格补明确的弃权原因与当前证据来源，复盘能区分脸未认出、完整外观不符、覆盖未知、特效方向未知、几何未确认和运动等待。保持未知状态，不靠历史值填补当前格。

**王者实施方向**：沿用已训练小地图定位和 512 模型，复核真实帧中的短暂出现、遮挡／重叠、地图缩放及前后台恢复；将画面质量、当前检测、跟踪和事件准入分段归因。确有失败时修正对应输入／关联／失效路径，冻结模型与阈值作为第一轮基线。轨迹记忆保持有限时效，新的可见证据与历史记忆分别记录。

**验收**：

- 至少一组已确认的真实视觉反例在生产回放中改善身份、权限或时序结果，逐样例列出前后输出。若最新基线已修复某项历史反馈，保留为回归并改选仍有证据的缺口。
- 消消乐按家族报告 miss、misclassify、false_swap、swap_miss，以及受影响的合法走法和 top-1／top-3。旧冻结集的身份认错与错误交换授权不增加，已确认的目标难样例漏认／过度弃权下降；零值仅适用于有真值的开发集。
- 覆盖、未知、运动、缺帧、同时间戳冲突、相邻格变更和新关卡反例通过；王者跟踪、再出现、观测过期及范围回归通过。Debug／混淆 Release 的完整状态和事件输出一致。
- 视觉改动纳入 W3 的软件成本门禁，P95 增幅不超过既有 10% 上限。新增复核限定在有依据的局部工作量；识别收益与处理开销一起报告。

主要入口：[Match3Sampler](../../android/app/src/main/java/com/openkhub/sensefield/Match3Sampler.java)、[外观目录](../../android/app/src/main/java/com/openkhub/sensefield/Match3VisualCatalog.java)、[运动判定](../../android/app/src/main/java/com/openkhub/sensefield/Match3AppearanceMotion.java)、[逐格确认](../../android/app/src/main/java/com/openkhub/sensefield/Match3CellConfirmation.java)、[王者感知与跟踪](../../native/src/mapassist.cpp)。规则依据继续采用[元素规则参考](../research/开心消消乐元素规则参考.md)，外观家族与玩法机制分别审阅。

## P0：处理负载与发热

### W3 — 先定位当前成本，再保留有效优化

先固定两款游戏的输入、时间轴、设置、模型、阈值和基线输出，分别测量采集／复制、定位与采样、HUD／规则排序、模型 forward、诊断和输出阶段。记录全进程 CPU、处理墙钟 P50／P95、工作次数、内存与帧间隔；worker CPU 继续单列。

王者沿用 512 输入模型。历史精确缓存命中约 2%，模型 forward 曾占原生墙钟 97.08%，因此优先核查实际推理频次、执行线程与阶段调度。消消乐优先核查稳定棋盘中的重复定位、采样、HUD 与规则计算；已有缓存和热档继续作为基线。采集或识别的复用必须有独立失效条件，保留对移动目标、局面变化、短暂进入和恢复画面的检查。

**候选进入默认路径的条件**：同机、同输入时间轴、同设置，至少三组成对测量并交替执行顺序；全进程 CPU 成本的配对降幅中位数达到 10%，处理 P95 增幅不超过既有 10% 上限。纯成本方案与完成 W2／V1 后的冻结功能基线比较，逐帧识别、合法动作、排序、高亮坐标与事件时序保持一致；W2／V1 的明确修复差异单独列证。再与公开 0.4.6 做整体成本和质量对照，原先的漏报／误报反例和提示时效门控全部通过。

每轮只比较一个改法。先选择最多两个有成本依据的方案；没有稳定收益或出现识别／时效退化时回退，保留失败数据，再决定后续范围。已有 FP16 运算改变检测输出而被拒绝，FP16 存储和内存池未见明确收益，继续沿用原默认值。工程 CPU 改善与真实温升分别报告。

方法与历史依据：[成本定位计划](../../validation/performance/HEAT_PHASE_PLAN_2026-10-08.md)、[执行路径试验](../../validation/performance/HEAT_RUNTIME_TRIALS_0_4_4_2026-10-08.md)、[帧处理策略](../../android/app/src/main/java/com/openkhub/sensefield/FrameProcessingPolicy.java)、[热量采集工具](../../scripts/monitor_android_heat.py)。

### W4 — 最终包的前台与温升证据

W2／V1／W3 工程检查完成后冻结候选 APK，并记录安装回读 SHA。先做不依赖游戏关卡的自动启动／停止、设置保持、语音故障恢复和固定输入持续运行，再使用正常游戏前台流程补真实成本及温升。

配对条件固定为同机、同环境、相近起始温度、相同亮度／热点／画质／帧率／耳机和充电状态。两款游戏分别记录游戏单独运行与开启辅助的对照；各模式至少 3×15 分钟。继承已有 43°C 电池温度停止线与明显烫手／不适停止条件，提前停止的记录保留为未完成。

**验收**：最终候选处理 P95 相对冻结基线增幅不超过 10%；匹配条件下的额外温升沿用既有 1°C 上限，内存与断档报告完整。公开宣称“发热降低”还需有相对基线的配对改善证据。后台固定图 900 秒、模拟器 P95 和系统未报告热状态各自保留其适用范围。

由工程端自动收日志与测量。用户正常开始／停止辅助即可；新录制随日常反馈收集。前台对照或外部实声条件暂缺时，继续完成其余工程工作，将此项明确列为待验；本项通过前不记“发热已收敛”。

## P1：在稳定链路上核查消消乐策略收益

W1／W2 完成后，复核已有日志中最后 1～3 个目标、特效备选和目标接触不足的片段。以[开心消消乐元素规则参考](../research/开心消消乐元素规则参考.md)和已审阅规则目录为依据，优先修复能在原始画面上复现的排序／识别问题。

魔力鸟按可靠任务收益选择交换目标；灰毛球按已确认的上下左右邻接清除和剩余任务排序，未知跳跃落点保持未知。饼干的周边接触、层数损伤和实际清除分别记录；规则参考中待核实的特效组合、花团机制和随机补子继续保留不确定性。

`Match3GoalOutcome` 当前依赖恰好两格互换的视觉证据，800ms 采样可能错过短交换态。本版先统计缺失原因，再决定是否补有界短窗口证据；目标数字减少或掉落变化不能单独证明玩家采用了提示。任何新增归因必须覆盖其他手动交换、连消、多步、重置、旧提示和缺帧反例。

P1 以现有资料可复现的问题为范围；待新证据的元素扩展进入后续迭代。独立准确率、真人采纳与通关收益保持独立验收，工程回放结果用于修复与回归。
