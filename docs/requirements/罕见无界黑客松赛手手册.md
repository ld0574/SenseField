## 02｜这不是一场传统黑客松

### 核心理念

> 我们想做的，不只是一场黑客松。  
> 比赛有终点，项目可以持续生长。

本次黑客松的重要特点：

- 所有赛题均来自真实患者和真实生活场景；
- 患者不是“被帮助者”，而是项目共创者；
- 一个赛题就是一个持续开放的开源项目；
- 可以个人参赛，也可以多人组队；
- 同一道赛题可以同时存在多支队伍、多个方案与不同技术路线；
- 赛前不做强制孵化，但会提前开放患者、疾病知识、导师、AI 与技术资源；
- 线下重点不仅是开发，也包括真实测试、资源连接与合作；
- 无论比赛结果如何，赛事期间形成的公开成果都需完成开源；
- 比赛结束后，有价值的项目可以继续由原团队或新贡献者接力。

### 四个关键词

1. **REAL｜问题来自患者**  
   不是命题作文，而是真实生活中的具体困难。

2. **TOGETHER｜患者参与共建**  
   解释需求、测试原型、给出反馈，一起判断是否有用。

3. **OPEN｜成果持续开源**  
   代码、设计、文档和经验沉淀下来，支持更多人复用与贡献。

4. **IMPACT｜从功能走向使用**  
   优先验证真实有效，再探索产品化与产业化。

> 不要求所有人创业，也不要求做出“大而全”的产品。一个真实、有用、可验证的小功能，同样值得认真完成。

## 04｜参赛规则 & 资源

> 参赛规则，先讲清楚。  
> 不要求统一节奏，但有共同的协作底线：**尊重患者、真实验证、成果开源。**

### Rule 01｜参与方式

**个人或团队，都欢迎。**

- 选择感兴趣的赛题进入项目群；
- 可以组队竞赛，也可以独立参赛；
- 同一项目允许不同方案并行探索；
- 同一赛题可以有多支队伍、多条技术路线；
- 组织方不强制分队；
- 需要伙伴时可在项目群发起招募。

### Rule 02｜赛前节奏

**提前探索，不强制作业。**

- 赛前开放共创是可选择的支持阶段；
- 不设置统一进度门槛；
- 越早提出具体问题，越容易匹配患者、导师、Token、算力或硬件等资源。

### Rule 03｜作品方向

**真实、有用、可验证。**

- 聚焦患者真实场景；
- 优先交付能运行、能体验或能被验证的具体功能；
- 已有开源原型的改善、有效的部分功能或 Demo 均可作为成果；
- 使用第三方作品时，需注明来源与许可。

### Rule 04｜现场展示

**讲清“做了什么、验证了什么”。**

展示内容应尽量包括：

- 功能或原型；
- 患者反馈及迭代依据；
- 当前不足；
- 下一步计划。

希望继续产品化的项目，可进一步提出：

- 试点需求；
- 制造需求；
- 产业合作需求；
- 资金/投资需求。

### Rule 05｜开源原则

**参赛即认同开源协作。**

比赛可公开成果应在赛事结束前按项目要求沉淀并开源，包括但不限于：

- 代码；
- 设计；
- 文档；
- BOM；
- 测试记录；
- 其他可复用成果。

具体许可证和贡献流程，以各项目正式规则为准。

### Rule 06｜赛后路径

**继续、合作，也允许接力。**

- 原团队可以持续维护；
- Khub 可根据项目情况继续提供支持；
- 原团队暂停后，已有开源成果仍可由社区贡献者继续推进；
- 商业合作或权利安排另行协商。

## 05｜开源，是参赛前提

> 一个赛题，一个持续成长的开源项目。

这 8 个项目是 Khub 社区持续建设的开源项目。比赛队伍是其中的参与者和贡献者，而不是项目唯一的长期载体。希望每一份有效探索都能留下来，成为后来者可以接着做的起点。

### 开源协作原则

1. **以 GitHub 为项目协作入口**  
   README、Issues、文档与版本持续更新。

2. **不只公开代码**  
   可公开的设计、BOM、测试过程和失败经验同样重要。

3. **尊重原创与贡献**  
   记录来源、贡献与署名；商业化另行明确合作安排。

4. **允许多人、多路线、长期接力**  
   让项目不因比赛或某支团队的结束而归零。

### 基本要求

无论：

- 是否获奖；
- 是否完成全部功能；
- 是否赛后继续；
- 是否未来进行商业化；

**比赛期间产生的可公开成果，都需要在赛事结束前完成整理与上传。**

包括但不限于：

- README / 项目说明；
- 需求与背景资料；
- 方案设计；
- 研究与技术探索记录；
- 源代码；
- CAD / 3D 模型；
- 硬件设计；
- BOM；
- 测试记录；
- 失败尝试与经验；
- 使用说明；
- 后续 Roadmap。

### 开源平台

- 基础开源平台暂定为 **GitHub**；
- Demo 展示平台可选用 **魔搭社区 ModelScope**。

### 特别说明：开源不等于公开患者隐私

以下内容不属于“必须公开”的范围：

- 患者隐私；
- 医疗数据；
- 个人身份信息；
- 未经授权的医学资料；
- 其他敏感信息。

涉及敏感信息时，以：

- 患者授权；
- 隐私保护；
- 安全边界

为第一原则。

### 开源是什么？对罕见病有什么用？

开源不是简单地“把代码放到网上”。在明确许可与边界的前提下，让更多人可以查看、使用、改进并分享项目成果，一起解决真实问题。

1. **SEE & REUSE｜让已有探索成为下一次起点**  
   代码、结构图、BOM、用户验证和失败经验可以被复用，让后来者不用反复从零开始。

2. **CONTRIBUTE｜让不同能力的人加入**  
   患者、开发者、设计师、医生和产业伙伴可以通过不同任务贡献，而不必由单个团队掌握全部能力。

3. **KEEP GROWING｜让项目不因比赛结束而归零**  
   8 个赛题属于 Khub 社区持续建设的开源项目；赛手可继续维护，也可以由新贡献者接力。

> 最重要的边界：开放的是获得相应授权、适合公开的项目成果；患者病历、影像、身份和其他敏感信息不会因为参与项目而自动开源。

## 开源协作中的选择与权利

参赛需要认同开源原则，但这不意味着放弃所有自主权。

1. **选择项目与参与方式**  
   可选择感兴趣的项目，个人探索或自主组队；同一赛题允许多支队伍、多种实现路线。

2. **获得贡献记录与合理署名**  
   代码、设计、文档、测试等贡献都可以被记录。具体版权、许可与署名方式，以项目规则和所签 CLA 为准。

3. **阅读协议，再决定是否参与**  
   签署前有权查看 CLA 与保密要求、提出问题；不同意相关条款，可不参与需要签署或接触受限数据的工作。

4. **选择继续、合作或暂停**  
   比赛结束后可继续维护、与社区合作，也可停止后续贡献；已按开源协议合法公开的版本，其既有使用许可通常不能单方收回。

5. **探索商业化，但遵守许可**  
   开源与商业化不矛盾；可探索产品、服务和产业合作，但应遵守适用许可证、第三方授权及另行约定的合作条款。

6. **尊重患者的知情、隐私与退出**  
   患者决定分享什么、授权做什么；任何成员都不得将受限资料上传公开仓库或未经批准的第三方 AI 工具。

## 06｜如何开始？

> 不用所有人同步推进。可以先独立探索，也可以先找伙伴；一旦明确方向，就把想法、问题和进展带回项目组。

### 01 进入感兴趣的项目组

- 阅读对应 README；
- 阅读疾病知识和已有讨论；
- 先理解患者的真实场景。

### 02 自行组队，组长更新组队信息

- 在项目群招募伙伴；
- 组长提交赛题、方向、成员、联系人及所需能力等信息；
- 独立参赛同样可以。

### 03 成员签署 CLA 与患者数据保密协议

- 先阅读正式文本；
- 确认贡献和资料使用边界；
- 在接触受限患者材料前完成必要手续。

### 04 形成产品与技术开发方案

明确：

- 目标场景；
- 计划实现的功能；
- 技术路线；
- MVP；
- 优先验证的假设；
- 所需资源。

### 05 在项目组内共创，开始开发

与患者、队友持续沟通，把：

- 需求确认；
- 代码；
- 设计；
- Issues；
- 测试结果

沉淀到合适的位置。

### 06 参加导师交流日 / Project Clinic

带着具体方案或卡点来，讨论：

- 技术可行性；
- 功能验证；
- 产品优化；
- 下一步资源需求。

> 不是强制汇报。

## 11｜如何与患者协作？

> 患者是本次赛事的重要共创者，即为赛手团队成员之一。

### 第一层：公共患者资料，所有赛手共享

包括：

- 需求介绍；
- FAQ；
- 患者资料；
- 已有场景和反馈。

### 第二层：具体问题确认

如果团队在推进过程中产生具体问题，可以提交给患者确认。

### 第三层：深度共创 / 测试

当项目进入原型、功能验证或真实使用阶段，可在患者**自愿、知情、授权**的前提下开展更深度的共创与测试。

整理原则：

- 只围绕项目所需的具体问题沟通；
- 优先使用已经整理好的公共资料，避免让患者反复解释同一背景；
- 原型测试、功能体验和反馈应以患者自愿为前提；
- 不以“参赛”为理由要求患者提供超出必要范围的个人、医疗或身份信息；
- 不将患者资料上传到公开仓库或未经批准的第三方 AI 服务；
- 如需记录影像、语音、测试数据或引用患者观点，应先取得明确授权；
- 患者可拒绝回答、暂停参与或退出；
- 团队应记录“验证了什么、得到什么反馈、因此如何修改”，而不是把患者仅作为最终验收角色；
- 技术团队不得把原型或 AI 输出包装成医疗诊断、治疗建议或替代专业医疗服务；
- 涉及安全风险的硬件、健康提醒或监测功能，应明确适用范围、失败场景和风险边界。

### 协作底线

1. **尊重**：患者不是“案例素材”，而是共同定义问题的人。  
2. **最小必要**：只收集解决当前问题真正需要的信息。  
3. **知情授权**：使用、记录、公开前先确认授权范围。  
4. **隐私优先**：开源成果与患者敏感资料严格分离。  
5. **可退出**：患者可随时停止参与，不影响其任何权益。  
6. **真实反馈**：保留失败测试、负面反馈和迭代依据。  
7. **不越界医疗**：产品验证不等同于临床诊疗或医疗器械认证。
