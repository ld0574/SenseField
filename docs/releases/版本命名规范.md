# 版本命名规范

从下一次构建交付起，应用版本统一使用 `a.b.c` 三段数字，例如 `0.3.0`、`0.3.1`、`0.3.2`。

## 每个新版本都递增

- 内部诊断、队友测试、患者试用和对外发布共用一条版本序列，不分内部、外部编号。
- 默认每交付一个包含新改动的版本，都递增版本号。通常递增最后一位：`0.3.0 → 0.3.1 → 0.3.2`。
- 同一份代码的重复构建和核验不算新版本。用户明确选择同版本修订覆盖时，可以保持版本名称和 `versionCode`；以 APK SHA-256 区分制品，保留修订前的包与摘要记录，并刷新 CDN 的 APK 和清单缓存。0.4.1 的 CDN 改造按此方式交付。
- 较大功能迭代可递增第二位并将最后一位置零，例如 `0.3.2 → 0.4.0`；第一位用于整体大版本变化。
- 不在版本号中添加 `alpha`、`beta`、`diagnostics`、`guide`、`internal`、日期或其他后缀。

## 构建与交付时同步检查

1. `android/app/build.gradle` 中的 `versionName` 是应用版本；必须符合 `a.b.c` 格式。
2. Android `versionCode` 是安装升级序号，新版本递增，不因版本号变化而重置；同版本修订遵守上面的明确例外。主线当前`0.4.3`使用`20`，此前`0.4.2`使用`19`、`0.4.1`使用`18`。消消乐独立分支已经有更高序号发布，同包名不允许以本包覆盖降级。
3. 同步 `scripts/build_android_preview.sh` 中的版本号和升级序号，避免交付旧包。
4. APK 文件名、SHA-256 校验文件、验证记录和发布说明必须对应同一次构建。允许文件名使用 `debug-candidate` 等标签来说明签名类型，应用版本本身仍为 `a.b.c`。
5. Git tag仅在明确需要时创建；提交代码和递增应用版本不要求创建tag。本次`v0.4.3`已由消消乐分支占用，使用`v0.4.3-main`记录主线0.4.3，APP版本名称仍为三段数字。默认保留既有标签；用户明确要求同版本覆盖发布时，可更新本版本主线标签与附件，并保留修订前源码及制品记录。队友的独立标签继续保留；覆盖修订保留发布前实际的Latest入口，不主动切换到其他版本。
6. 发布说明与使用文档放在 `docs/releases/<版本>/`；APK、ZIP、校验文件与构建元数据放在 `output/releases/<版本>/`。

旧记录中的 `0.3.0-alpha.1`、`0.3.0-alpha.1-diagnostics` 和对应 APK 文件名保留原样，作为当时的构建证据，不回改历史版本号、哈希或签名记录。
