# 版本命名规范

应用版本使用 `a.b.c` 三段数字，当前开发候选为 `0.4.8 / versionCode 27`，稳定公开版为 `0.4.7 / versionCode 24`。

此前已有 `0.4.9 / code26` 预发布；本次候选命名为 `0.4.8`，但内部序号继续递增到 27。0.4.9 客户端的旧更新器按版本名称拒绝回退，因此这部分用户需下载 APK 手动覆盖安装；保留相同包名与证书，无需卸载。后续版本仍应同时递增名称和内部序号，避免继续交叉命名。

## 版本递增

- 一般修订递增最后一位，较大功能迭代递增第二位并将最后一位置零。
- Android `versionCode` 是升级序号，新版本必须递增，不随版本名称重置。
- 同一代码重复构建不产生新版本。同版本修订以 APK SHA-256 区分，使用相同签名并保存原制品记录。
- 用途、测试范围和发布渠道写在发布说明中，不加入应用版本名称。

当前更新器能通过 APK 摘要区分同版本修订；旧客户端可手动覆盖安装。同包名、同证书和正确版本关系是保留本地设置升级的前提。

## 交付一致性

1. 在 `android/app/build.gradle` 声明版本；构建脚本与发布校验从该配置读取版本。
2. 从同一份最终签名 APK 读取包名、版本、字节数和 SHA-256，不手工拼接清单。
3. 源码提交、版本说明、APK 和校验记录应能相互对应。
4. 说明放在 `docs/releases/<版本>/`，二进制与构建元数据放在 `output/releases/<版本>/`。
5. 公开 Release 使用对应标签，如 `v0.4.7`；保留已发布源码和制品记录。

发布操作见 [发布检查](GITHUB发布检查清单.md) 与 [分发流程](../../deploy/assistant/CDN发布.md)。
